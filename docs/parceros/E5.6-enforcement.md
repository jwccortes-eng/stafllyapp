# E5.6 — Parceros Consent + Visibility Enforcement

**Status at close of E5.6:** capability implemented, **NOT activated** in production.
Production runs `PARCEROS_CONSENT_MODE=log_only` (default). Flipping to `enforce`
requires a separate, explicit E5.7 approval.

## What E5.6 ships

- `supabase/functions/_shared/parceros-consent-decider.ts` — pure decider
  `decideEnforcement(status, visibility, mode)`. No DB, no env reads, no side
  effects.
- `supabase/functions/_shared/parceros-enforce_test.ts` — 12 Q-tests (Q1–Q12) +
  `normalizeMode` coverage.
- `supabase/functions/parceros-sync/index.ts` — integrated decider. When and
  only when `PARCEROS_CONSENT_MODE=enforce`, blocks payloads that fail consent
  or `profile_visibility='hidden'`. Blocked payloads are **not** pushed and
  **not** queued in `parceros_event_queue`.

## What E5.6 does NOT change

- `parceros-payload.ts`, `parceros-forbidden-keys.ts`.
- `PARCEROS_GUARDRAIL_MODE` (E5.3 guardrail).

## Modes

| Mode | Behavior |
|---|---|
| `off` | Consent check skipped entirely. Push proceeds (legacy). |
| `log_only` (**default, production**) | Consent + visibility evaluated; status logged with `would_block_in_enforce`; push proceeds regardless. |
| `enforce` | Push and queue insert are skipped when decider returns `allow=false`. Reason logged as `blocked_reason`. |

## Decider contract

```ts
decideEnforcement(status, visibility, mode) → {
  allow: boolean,
  blocked_reason:
    "consent_missing" | "consent_revoked" | "consent_denied"
    | "consent_error" | "visibility_hidden" | null,
  mode,
  consent_status,
  would_block_in_enforce: boolean,
}
```

Fail-closed: consent query errors map to `status="error"` and block under enforce.

Per-field visibility (`show_reputation`, `show_work_history`, `show_skills`,
`show_city`, `show_photo`, `show_first_name`, `show_last_name`) is applied
inside `toParcerosSyncBody` and verified by the E5.5 suite. The decider does
not touch per-field logic.

## How to activate enforce (requires E5.7 approval)

Precondition: data-sharing consent adoption ≥ 80% of active workers, measured
for ≥ 7 consecutive days, with zero PII in `parceros_consent_check` logs.

1. Run impact query (read-only):
   ```sql
   WITH latest AS (
     SELECT DISTINCT ON (worker_profile_id)
       worker_profile_id, granted, revoked_at
     FROM worker_consent_records
     WHERE consent_type='data_sharing'
     ORDER BY worker_profile_id, COALESCE(updated_at, created_at) DESC
   )
   SELECT
     CASE
       WHEN l.worker_profile_id IS NULL THEN 'missing'
       WHEN l.revoked_at IS NOT NULL THEN 'revoked'
       WHEN l.granted THEN 'granted'
       ELSE 'denied'
     END AS status,
     count(*)
   FROM worker_profiles wp
   LEFT JOIN latest l ON l.worker_profile_id = wp.id
   GROUP BY 1;
   ```
2. Flip env var **per environment**, never globally in one step:
   - `Stafly Demo` first.
   - Single pilot production tenant.
   - Global production.
3. Set `PARCEROS_CONSENT_MODE=enforce`. No code change required.

## Rollback to log_only

- Set `PARCEROS_CONSENT_MODE=log_only` (or remove the var; `log_only` is the
  default). Effective on next request, no redeploy needed.
- Blocked payloads are **not** queued (intentional). They are re-emitted by
  the normal sync triggers once consent is granted. There is **no retry queue
  for blocked events** and that is the approved design.

## Risks pending for E5.7

  premature flip would block everything.
- ConsentCenterCard adoption flow needs to be live and measured before E5.7.

- Decide whether blocked events should leave an audit row in
