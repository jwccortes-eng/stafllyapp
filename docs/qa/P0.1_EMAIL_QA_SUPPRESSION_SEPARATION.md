## 1. Suppression model — before / after

### Before
| Capa | Comportamiento |
|---|---|
| Proveedor (Lovable) | Supresión global por dirección + dominio remitente. Rebote, queja y baja bloquean **todo** el correo de app. |
| Registro local `public.suppressed_emails` | Solo tres razones (`bounce`, `complaint`, `unsubscribe`), **sin alcance**. Se escribía desde el webhook pero **no se consultaba en ningún envío**. |
| Código de envío | `sendRawEmail` sin categoría: recovery, invitación y activación eran indistinguibles. |

Riesgo material: una baja de marketing (o una queja) quedaba registrada con el mismo peso que un rebote duro; cualquier futuro uso del registro local habría bloqueado recuperación de PIN y activación de cuenta.

### After
| Elemento | Implementación |
|---|---|
| Categorías de envío | `security`, `transactional_access`, `operational`, `marketing` (`_shared/email-policy.ts`). |
| Alcances de supresión | `marketing`, `non_essential`, `all` (columna `scope` en `suppressed_emails`, con CHECK e índice `(email, scope)`). |
| Origen → alcance | `unsubscribe → marketing`, `complaint → non_essential`, `bounce/provider/manual → all`. |
| Gate local | `localSuppressionBlocks()` invocado dentro de `sendRawEmail`; nunca amplía el bloqueo más allá del alcance. |
| Etiqueta → categoría | `pin_recovery_code → security`, `invite_email` y `portal_activation → transactional_access`, resto `operational`. |

## 2. Marketing vs transactional — reglas efectivas (verificadas)

Matriz ejecutada sobre el modelo real (`scopeBlocksCategory`):

| Origen | Alcance | security | transactional_access | operational | marketing |
|---|---|---|---|---|---|
| unsubscribe | marketing | PASS | PASS | PASS | BLOCK |
| complaint | non_essential | PASS | PASS | BLOCK | BLOCK |
| hard bounce | all | BLOCK | BLOCK | BLOCK | BLOCK |

Conclusión: **una baja de marketing no puede inutilizar activación, recuperación, magic link ni verificación**.

Nota de plataforma (fuera del control del repositorio): la supresión del proveedor sigue siendo autoridad de entrega y hoy no distingue categorías para correos de app. Los correos de **auth** (signup, magic link, recovery de contraseña) viajan por el hook de auth y no quedan bloqueados por una baja de app. El caso residual es el **código de PIN por email**, que sí es un correo de app: si el proveedor lo bloquea, el backend devuelve `SUPPRESSED` explícito y el admin recibe la alternativa (WhatsApp / enlace directo) en vez de un falso éxito.

## 3. Bounce behavior
- Registra evento en `email_send_log` y entrada `scope = 'all'` en `suppressed_emails`.
- **No** borra usuario, **no** desactiva employee, **no** toca membresías, Passport, payroll ni otros tenants. El handler solo hace `insert` de log y `upsert` de supresión.
- Reversible: corregir la dirección y eliminar la fila de supresión restaura los envíos.

## 4. Complaint behavior
- Registra evento (`complained`) y supresión con `scope = 'non_essential'`.
- Bloquea marketing y operativo no esencial; **no** bloquea seguridad ni acceso.
- Queda explícitamente diferenciada de una baja de marketing (razón y alcance distintos, ambos persistidos).

## 10. Delivery truth (UX admin)
Estados separados y honestos: `created` → `queued` → `sent` / `failed` / `suppressed` / `bounced`.
- `sent` solo cuando el proveedor aceptó el envío.
- `suppressed` con mensaje humano: restricción de entrega + alternativa (WhatsApp o enlace).
- **Se eliminó la derivación de `delivered` y `opened`** desde el log de envío (`src/lib/invitation-status.ts`): la plataforma no emite acuses de entrega ni de apertura, por lo que nunca se muestra "Entregado" sin recibo real.

## 11. URL / auth flow
- Enlaces construidos con `src/lib/app-url.ts` → `https://staflyapps.com` (solo localhost en desarrollo). Ningún enlace apunta al preview de Lovable.
- Invitación/activación → `/activate/:token` (wizard que crea usuario y PIN). Activación masiva → `https://staflyapps.com/portal`.
- Plantillas de auth usan `SITE_URL = https://staflyapps.com` y el `url` firmado del hook, con su expiración original intacta.
- Ningún token, código o clave aparece en este reporte ni en logs (los logs registran `message_id`, nunca el contenido).

## 12. Idempotency
- Invitación individual: `invite-email-<invitation_id>` (estable por invitación).
- Activación masiva: `bulk-activation-<employee_id>-<YYYY-MM-DD>` (un envío por persona y día, reintentos deduplicados).
- Recovery: clave única por solicitud (cada código es un envío legítimo distinto).
- Webhook: `upsert` por `email` con `onConflict` → eventos duplicados son idempotentes; el log de eventos duplicados no altera estados de invitación.
