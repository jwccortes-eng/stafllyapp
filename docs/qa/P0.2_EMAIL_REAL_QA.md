## 2. Hallazgo bloqueante

Los tres envíos aceptados fueron **rechazados por la plataforma en el despacho**, con el mismo motivo:

> `permanent send failure: Domain notify.staflyapps.com is not allowed to send: The domain is unverified and requires DNS configuration`

El chequeo de estado del dominio lo confirma: DNS del subdominio verificado, pero **la ruta de envío del proyecto no está lista** ("Timed out waiting for email delivery path verification"). Es decir: **hoy no sale ni un solo correo de aplicación**, ni a QA ni a nadie. Esto es configuración de entrega, no un defecto del código de este proyecto.

**Consecuencia directa: no se pueden conectar Comunicados Oficiales al correo.** Un comunicado con acuse que no llega es peor que no enviarlo.

## 3. Segundo hallazgo: verdad de entrega todavía optimista

El backend devolvió `delivery: SENT` y escribió `status = sent` en el registro local para tres correos que la plataforma rechazó segundos después. La aceptación del API **no** es entrega ni despacho.

Estado real vs mostrado:

| Registro | Mostrado al admin | Realidad |
|---|---|---|
| #1, #2, #3 | `sent` | `rejected` (fallo permanente) |
| #4 | `failed` | correcto |

Corrección pendiente (no aplicada: este turno era solo QA): el estado inmediato debe ser `accepted` / `en despacho`, y `sent` únicamente cuando existe evento de envío confirmado; los eventos `rejected` deben reconciliar la invitación a fallo. No se tocó código para no violar la restricción del task.

## 4. Idempotencia — validada

Con `invitation_id` presente, la clave es `invite-email-<invitation_id>`: el reintento con la misma clave **no** generó un segundo despacho; la plataforma respondió 409 exigiendo clave nueva y el backend lo registró como fallo, sin duplicar correo. Sin `invitation_id` la clave incluye timestamp, así que cada llamada es un envío distinto por diseño.
