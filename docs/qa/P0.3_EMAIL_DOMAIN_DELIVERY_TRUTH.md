- `staflyapps.com` → NS de IONOS (`ns1092.ui-dns.org` y pares)

Esa es la causa exacta del rechazo del proveedor. Registros a crear en IONOS:

| HOST | TYPE | VALUE | TTL |
|---|---|---|---|

está: no afecta al subdominio delegado.

## 5. Fix de delivery states

Modelo canónico nuevo en `supabase/functions/_shared/email-delivery-state.ts`:

```
created → queued → accepted → sent → delivered
                      ↘ rejected / failed / suppressed / bounced / complained / rate_limited
```

- `canAdvance()` impone progreso monótono: un evento tardío nunca retrocede el
  estado.
- `PENDING_RECONCILIATION` = `created | queued | accepted`: lo que aún no prueba
  despacho.
- `isDomainUnverified()` clasifica el rechazo por dominio sin verificar.

Base de datos (`public.email_send_log`):

- CHECK ampliado a `created, pending, queued, accepted, sent, delivered,
  rejected, failed, suppressed, bounced, complained, rate_limited, dlq`.
- El índice único de mensaje ya no premia la aceptación del API: aplica a
  `sent` y `delivered`.
- Los disparadores de sincronización de invitaciones se reescribieron y ahora
  reaccionan también a `UPDATE OF status` (eventos tardíos), mapean `accepted →
  queued`, `rejected → failed`, y `delivered_at` solo se sella con un evento
  real de entrega.

## 6. Before / after de la semántica SENT

| | Antes | Ahora |
|---|---|---|
| Respuesta 2xx del API | `status: 'sent'`, `delivery: 'SENT'` | `status: 'accepted'`, `delivery: 'ACCEPTED'` |
| Registro local | fila `sent` inmediata | fila `accepted`, reconciliable |
| `sent` significa | "el API aceptó la petición" | "el proveedor confirmó el despacho efectivo" |
| `delivered` | derivado/inventado (se había eliminado) | solo con evento real de entrega; la plataforma no lo emite hoy |
| Rechazo en despacho | invisible: quedaba como `sent` | `rejected` + código `DOMAIN_UNVERIFIED` |

`sendRawEmail` devuelve ahora `{ accepted: true }` en vez de `{ sent: true }`;
los tres remitentes (`send-invite-email`, `bulk-portal-invite`,
`_shared/pin-recovery`) registran `accepted`.

## 7. Webhook / event reconciliation

- `handle-email-events` (bounce, complaint, unsubscribe) es ahora idempotente:
  deduplica por `event_id` en `metadata` antes de insertar y solo avanza el
  estado de intentos recientes que aún no son terminales. Una reentrega del
  mismo evento no crea filas ni cambia nada.
- Nueva función `reconcile-email-delivery`: lee los eventos reales del proveedor
  (`listEmailLogs`) de las últimas 72 h y avanza cada registro `accepted` a
  `sent`, `rejected`, `bounced`, `complained`, `suppressed` o `rate_limited`.
  El `UPDATE` está acotado a estados no probatorios, así que reejecutarla es
  seguro y los eventos tardíos se aplican sin duplicar ni retroceder.
- Eventos cubiertos: `sent`, `rejected`, `bounced`, `complained`,
  `unsubscribed`, `suppressed`, `rate_limited`. `delivered` no existe en la
  plataforma y no se simula.

Funciones desplegadas: `send-invite-email`, `bulk-portal-invite`,
`employee-auth`, `handle-email-events`, `reconcile-email-delivery`.

## 8. Admin UX

- Un envío aceptado ya no dice "Invitación enviada": dice **"Invitación en
  camino"** con el detalle de que la entrega se confirma al despacharse.
- Estado `queued` = "En camino" · "Solicitud aceptada; falta la confirmación de
  despacho del proveedor".
- Estado `rejected` = **"No se pudo enviar"**, detalle técnico opcional "El
  proveedor rechazó el envío". No se muestra el mensaje crudo del proveedor.
- La campaña masiva rotula "En camino" / "Activado" / "No enviado" en vez de
  "Sent".
- No se expone dominio, código interno ni traza al usuario final.

## 11. Riesgos restantes

1. **Bloqueante:** sin los dos registros NS en IONOS no sale ningún correo de
   aplicación — ni invitaciones, ni activaciones, ni recuperación de acceso.
2. La reconciliación se apoya en el emparejamiento por destinatario dentro de
   72 h; con dos envíos al mismo correo en la misma ventana, el evento más
   avanzado gana. Es conservador (nunca degrada), pero no es un enlace 1:1 por
   `message_id` — la plataforma no lo expone en sus eventos.
3. `reconcile-email-delivery` no tiene disparador programado: hoy se invoca a
   demanda. Conviene programarla cuando el dominio esté activo.
4. `delivered` existe en el modelo pero la plataforma no emite acuse de entrega:
   seguirá sin usarse hasta que exista el evento.
5. 211 avisos preexistentes del linter de seguridad (search_path, SECURITY
   DEFINER); ninguno introducido aquí.
