## 1. Command Center Flow

The admin Command Center (`/app` on desktop, mobile command-center grid on 390×844) is organized into five operational zones.

### 1.1 Needs Attention
- Shifts flagged for operator review (coverage gaps, conflicts, unresponded requests).
- Drills directly into Manage Team for action.

### 1.2 Today
- Active shifts whose `start_date` falls within the current calendar day window.
- Shows real-time counts of assigned, confirmed, pending, and missing workers.

### 1.3 Upcoming
- Shifts scheduled beyond today, sorted chronologically.
- Allows proactive staffing before deadlines.

### 1.4 Recent Responses
- Recent worker accept/reject events surfaced from `shift_assignments.response_status`.
- Drives follow-up actions (fill gaps, replace decliners).

### 1.5 Claims Pending
- Unresolved worker-initiated shift requests (`shift_requests` with `status = pending`).
- Admin can approve or reject via UI or RPC.

## 2. Manage Team Flow

The Manage Team module is the primary operator interface for per-shift staffing. It is the canonical path for assignments, replacements, and coverage fixes.

### 2.1 Overview
- High-level shift card: capacity, filled count, open slots, response summary.
- Entry point to drill into staffing tabs.

### 2.2 Assigned
- Workers already assigned to the shift (`shift_assignments.status` in `pending`, `confirmed`, `accepted`).
- Shows name, employer ID, readiness badge, assignment status.

### 2.3 Claims
- Worker-initiated claims or requests tied to this shift.
- Admin can resolve each with approve/reject actions.

### 2.4 Issues
- Readiness or policy conflicts (e.g., blocked preference, outside grace period, duplicate assignment).
- Issues are warnings, not hard blocks — operator decides.

### 2.5 Recommended
- Intelligent worker shortlist generated by `worker-recommendation.ts`.
- Groups: **Best match**, **Good options**, **Use with caution**.
- Each candidate shows Why? explanation (worked-here history, preference fit, readiness state).

## 3. Location Model

### Canonical hierarchy
| Concept | Table / Column | Purpose |
|---------|---------------|---------|
| **Shift job site / venue** | `locations` | Where work physically happens. Canonical. |
| **Billing / picker tech debt** | `locations_v2` | Parallel system used in billing and legacy pickers. To be consolidated. |
| **Work location** | `scheduled_shifts.location_id` | FK to `locations`. Drives worked-here history and job site. |
| **Meeting / pickup point** | `meeting_point_location_id` | Where workers gather before transport. Never treated as a worked-here venue. |
| **Free-text meeting point** | `meeting_point` (text column) | Preserved for display. Not a location FK. |

### Safety rule
- **Never** use `meeting_point` or `meeting_point_location_id` as a worked-here venue in worker history.
- Worked-here history is derived exclusively from `scheduled_shifts.location_id`.

## 4. Assignment Flow

### 4.1 Operator path
1. Operator opens **Manage Team → Recommended**.
2. Operator selects a worker from the Recommended list (or searches the full roster).
3. UI calls `assign_worker_to_shift` (source: `mobile_manage_team` on mobile, desktop equivalent on desktop).

### 4.2 Database outcome
- New row in `shift_assignments`:
  - `status = 'pending'`
  - `response_status = 'pending'`
  - `response_required = true`
- Audit row inserted in `shift_audit_log`:
  - `action = 'assignment_created'`
  - `source = 'mobile_manage_team'`
  - `reason` provided by operator or default
- Worker notification created in `notifications`.
- Shift assignment counts updated in UI (assigned +1, pending +1).

### 4.3 What does NOT happen
- No `time_entries` created.
- No `payroll_adjustments` created.
- No `attendance` state changed.
- No hard delete of any record.

---

## 5. Worker Response Flow

### 5.1 Worker path (Portal)
1. Worker logs into `/portal` (phone + PIN or session).
2. Worker sees shift assignment in their schedule/shift list.
3. Worker taps **Accept** or **Reject**.
4. Portal calls `worker_respond_to_shift_assignment` RPC.

### 5.2 Accept outcome
- `shift_assignments.status` → `confirmed`
- `shift_assignments.response_status` → `accepted`
- `shift_assignments.responded_at` → `now()`
- Audit action: `worker_accepted`
- Admin notification created (real-time if ops dashboard is subscribed).

### 5.3 Reject outcome
- `shift_assignments.status` → `rejected`
- `shift_assignments.response_status` → `rejected`
- `shift_assignments.responded_at` → `now()`
- Audit action: `worker_rejected`
- Admin notification created; replacement workflow may trigger.

### 5.4 What does NOT happen
- No `time_entries` created on accept.
- No payroll calculation triggered.
- No attendance clock-in/out recorded.
- Assignment row is **not** deleted (soft state transition only).

## 6. Safety Rules

| Rule | Enforcement |
|------|-------------|
| Payroll only pays real `time_entries` or approved day-pay validation | Payroll engine ignores scheduled hours for payment |
| Scheduled hours never pay payroll | UI displays scheduled hours for planning only; never in pay stubs |
| Assign / accept does not create `time_entries` | Time entries are created only by kiosk clock, portal clock, or manual admin entry |
| Attendance remains separate | `attendance_status` on `shift_assignments` is independent of assignment status |
| No hard deletes | All removals use `status` transitions (`pending` → `cancelled`, `removed`, etc.) |
| Audit every state change | `shift_audit_log` captures `before_data`/`after_data` JSONb for every mutation |
| Tenant isolation | Every RPC and RLS policy filters by `company_id` or `auth.uid()` scoped to tenant |

## 7. Worker Readiness

### Grace window
- **60-day grace** applies to:
  - Quality Staff
  - MyStaff
  - JKitchen
- Workers with `profile_status = 'incomplete'` or `onboarding_status = 'pending'` **inside** the grace window may still be assigned (with a warning badge).

### Blocking rules
| State | Assignable? | Badge |
|-------|-------------|-------|
| `ready` or `active` | Yes | Ready |
| `incomplete` inside grace | Yes (warned) | Grace |
| `inactive` | No | Blocked |
| `blocked` | No | Blocked |
| `incomplete` outside grace | No | Blocked |

## 8. Preferences and Intelligence

### 8.1 Preference types
| Type | Effect |
|------|--------|
| **Preferred** | Worker ranks higher in Recommended for this client/location |
| **Prequalified** | Worker is eligible but not top-ranked |
| **Block** | Worker is excluded from Recommended for this client/location (operator can still force-assign) |

### 8.2 Worked-here history
- Derived from `scheduled_shifts.location_id` where the worker was assigned and the shift occurred in the past.
- Drives the **Best match** grouping in Recommended.

### 8.3 Recommended groups
| Group | Criteria |
|-------|----------|
| **Best match** | Worked here before + preferred + ready state |
| **Good options** | Prequalified or partial match |
| **Use with caution** | Grace-period incomplete, no history, or operator override required |

### 8.4 Why? explanation
- Every Recommended candidate shows a concise reason string:
  - "Worked Heiden Rd 3 times"
  - "Preferred for this client"
  - "In grace period — incomplete profile"
  - "No location history"

## Daily Close / Captain Verification (Phase 17C)

### 1. Purpose
- Captures **operational evidence** after a shift ends (staff present, no-shows, lates, incidents, uniform compliance, client feedback).
- Lets admins / María / Keury review what actually happened on the ground.
- **Does NOT approve payroll.** Payroll remains driven by `time_entries` and the existing reconciliation pipeline. Closeout is purely operational truth.

### 2. Data Model
- **Table:** `shift_closeout_reports` (one row per shift).
- **Lifecycle status:** `draft` → `submitted` → `reviewed` | `rejected`.
- **Admin review_status:** `approved`, `needs_followup`, `escalated`, `rejected`.
- **Auto-stamped by triggers:** `submitted_at`, `reviewed_at`, `reviewed_by`.
- **Audit actions written to `shift_audit_log`:**
  - `closeout_updated`
  - `closeout_submitted`
  - `closeout_reviewed`

### 3. Permissions
- **Submit operational facts:** captain, shift_admin, admin, manager, owner, developer.
- **Review (set review_status / move to reviewed/rejected):** admin, manager, owner, developer only.
- **Submitter cannot self-review** — enforced by `trg_shift_closeout_guard` + RLS policy `closeout_update_submitter_operational`.
- **Reviewed/rejected rows are locked** for non-admin users (no further edits).
- Immutable for non-admins: `company_id`, `shift_id`, `submitted_by`, `role`.

### 4. UI Surfaces
- **`MobileShiftOperationsSheet`** → new **Daily Close** section:
  - `CaptainCloseoutForm` (counts, notes, uniform, feedback, Save draft / Submit).
  - `AdminCloseoutReview` (approved / needs_followup / escalated / rejected).
  - `CloseoutSummaryCard` (compact summary or empty state).
- **Manage Team → Issues tab** flags today / past published shifts:
  - `closeout-missing` (warn)
  - `closeout-pending-review` (info)
  - `closeout-incidents` (bad)
- **Command Center → `DailyCloseKpiPanel`** — trailing 14 days:
  - Missing closeouts
  - Pending review
  - Shifts with incidents

### 5. Safety Rules (hard guarantees)
- ❌ Does **not** create or edit `time_entries`.
- ❌ Does **not** modify payroll (`payroll_adjustments`, periods, totals).
- ❌ Does **not** modify `attendance_status` or attendance calculations.
- ❌ Does **not** approve pay.
- ❌ Does **not** modify `shift_assignments`.
- ❌ Does **not** modify `scheduled_shifts`.
- ❌ Does **not** touch worker portal auth.
- ✅ Writes only to `shift_closeout_reports` (+ best-effort `shift_audit_log`).

## Payroll Review Queue v1

### 1. Purpose
- Read-only triage surface for María before payroll review.
- Helps surface issues before approval/reconciliation.
- Does not calculate, approve, post, or pay payroll.

### 2. Route
- `/app/payroll-review-queue` (admin/developer only, tenant-scoped).

### 3. Source of truth (unchanged)
- Connecteam imports / `period_base_pay` / `historical_payroll_entries` remain payroll authority.
- Stafly native TimeClock is **not** a payroll source.
- Scheduled hours are **never** payable hours — used only as discrepancy signals.

### 4. Default period selection
- Current period containing today, else
- Most recent period with `period_base_pay` rows, else
- Most recent past period.
- Never auto-selects a future high-sequence period (e.g., #165).

### 5. Buckets
1. Ready to review
2. Needs employee match
3. Time mismatch
4. Assignment without clock/pay
5. Clock/pay without assignment
6. Day-pay needs validation
7. Driver/transport payment
8. Manual adjustment pending
9. Worker dispute
10. Missing docs/profile
11. Closeout conflict
12. High-risk / over-threshold

### 6. Safety
- No DB writes, no schema changes, no payroll calculations.
- No period locking/posting, no TimeClock source switch.
- No changes to `time_entries`, `movements`, `pay_periods`, `payroll_adjustments`, `shift_assignments`, `scheduled_shifts`, `shift_closeout_reports`, or `shift_rides`.
